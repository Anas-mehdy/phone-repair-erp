# Phone Repair ERP MVP Implementation Plan

## Architecture Direction

This MVP is a web app first. It should stay simple now, while the backend and database remain ready for a future Flutter mobile app and partial offline sync.

Do not build the mobile app, local offline database, or sync engine in the MVP.

Use this flow:

```text
UI -> Server Actions or API Routes -> Services -> Prisma
```

Do not add a full repository pattern unless the codebase clearly needs it later.

## Core Principles

- Keep business logic out of UI components.
- Put workflow rules in service modules.
- Let Server Actions or API Routes handle request validation, session checks, and calling services.
- Use Prisma directly from services for the MVP.
- Use UUID primary keys for all core records.
- Use `shopId` everywhere, even though the MVP starts with one shop.
- Start with one shop and one owner user.
- Prepare a simple `UserRole` enum with `OWNER` and `STAFF`, but do not build complex roles or permission management now.
- Use soft deletes with `deletedAt` for business data.
- Include `createdAt`, `updatedAt`, `deletedAt`, `version`, and `clientGeneratedId` where useful for later sync.
- Keep repair status history append-only.
- Keep inventory movements append-only.
- Do not depend on sequential IDs for identity, ordering, sync, or conflict handling.
- Generate human-facing numbers separately from primary keys.

## Human-Facing Numbers

UUIDs are the real primary keys. Human-facing numbers are separate fields:

- `ticketNumber` for repair orders
- `invoiceNumber` for invoices
- `receiptNumber` for sales if needed

These numbers can be generated by backend services and scoped by `shopId`.

## MVP Scope

1. Repair Orders
2. Customers
3. Inventory
4. Simple POS / Sales
5. Invoices / Receipts
6. WhatsApp sharing via `wa.me`
7. Dashboard

- Telegram bot
- Flutter mobile app
- Offline local database
- Offline sync engine

- Multi-branch logic
- Complex roles and permissions

## Backend Structure

Keep the backend small and direct:

- UI components submit to Server Actions or API Routes.
- Server Actions/API Routes validate input, check the current user/shop, and call services.
- Services contain business logic, transactions, and Prisma calls.
- Prisma owns database access.

Recommended service modules:

- `customerService`
- `repairOrderService`
- `inventoryService`
- `salesService`
- `invoiceService`
- `paymentService`
- `whatsappService`
- `dashboardService`

Avoid creating repository classes in the MVP unless Prisma access becomes duplicated or difficult to maintain.

## Authentication

Keep authentication simple:

- Create one shop.
- Create one owner user.
- Store `shopId` on all important records.
- Always scope reads and writes by `shopId`.
- Use `UserRole` with `OWNER` and `STAFF` only as a future-ready enum.
- Do not build permission screens, role management, or complex access policies in the MVP.

## Payments And Invoices

Payments are invoice-centered.

- A repair order can generate an invoice.
- A sale can generate an invoice.
- Payments link to invoices, not directly to repair orders or sales.
- Invoice status supports unpaid, partially paid, paid, and void states.
- Partial payments are represented as multiple `Payment` rows against one `Invoice`.
- Sale and repair payment state should be derived from the invoice when possible.

This avoids duplicating payment logic across repairs and POS.

## Inventory

Inventory must use append-only movement logs:

- `InventoryItem.quantity` stores the current quantity for fast reads.
- Every stock change creates an `InventoryMovement` row.
- Sales, manual adjustments, returns, stock intake, and repair part usage all create movements.
- Normal business flows should not edit or delete movement rows.

## Sync-Ready Design

Do not build offline sync now.

Only prepare the schema and services using:

- UUID primary keys
- `shopId`
- `clientGeneratedId` where useful
- `createdAt`
- `updatedAt`
- `deletedAt`
- `version`
- append-only logs for critical changes

Expected future offline flows:

- create customer offline
- create repair order offline
- update repair status offline
- create simple sale offline
- sync changes when internet returns

Conflict handling is not required now.

## Database Rules

- Core records use UUID primary keys.
- Important business tables include `shopId`.
- Important business tables include `createdAt`, `updatedAt`, `deletedAt`, and `version`.
- Tables that may receive offline-created records later include `clientGeneratedId`.
- Use soft deletes for business data.
- Use append-only tables for repair status changes and inventory movements.
- Scope uniqueness by `shopId` where appropriate.
- Do not model future branches or multi-tenant hierarchy beyond `shopId` in the MVP.

## Prisma Schema

The Prisma schema lives in `prisma/schema.prisma`.

It includes:

- `Shop`
- `User`
- `Customer`
- `RepairOrder`
- `RepairStatusHistory`
- `InventoryItem`
- `InventoryMovement`
- `Sale`
- `SaleItem`
- `Invoice`
- `Payment`

## Implementation Phases

### Phase 1: Foundation

- Set up the web app framework.
- Configure Prisma and database connection.
- Add basic authentication.
- Seed one shop and one owner user.
- Add service modules.
- Ensure every operation is scoped by `shopId`.

### Phase 2: Customers

- Create, edit, list, search, and soft delete customers.
- Store `clientGeneratedId` for future offline-created customers.
- Keep customer business logic in `customerService`.

### Phase 3: Repair Orders

- Create repair orders with customer, device, issue, estimate, and due date.
- Generate `ticketNumber`.
- Store current repair status on `RepairOrder`.
- Append every status change to `RepairStatusHistory`.
- Allow repair orders to generate invoices.

### Phase 4: Inventory

- Create and edit inventory items.
- Store current stock in `InventoryItem.quantity`.
- Create an `InventoryMovement` for every stock change.
- Support stock intake, adjustment, sale usage, return, and repair part usage.

### Phase 5: POS / Sales

- Create simple sales with line items.
- Generate `receiptNumber` if needed.
- Decrease inventory through append-only `InventoryMovement` rows.
- Allow customer to be optional for walk-in sales.
- Allow sales to generate invoices.

### Phase 6: Invoices And Payments

- Generate invoices for repair orders and sales.
- Generate `invoiceNumber`.
- Track invoice status.
- Record payments against invoices only.
- Support unpaid, partially paid, and paid invoices.

### Phase 7: WhatsApp Sharing

- Generate `wa.me` links for repair updates, invoices, and receipts.
- Do not use the WhatsApp API.
- Do not store generated WhatsApp links in the database.
- Generate links dynamically from current `Invoice`, `RepairOrder`, `Customer`, and `Shop` data.
- Use `Customer.phoneNormalized` when available, otherwise clean `Customer.phone` before building the link.
- Keep message generation in service code, not UI components.

### Phase 8: Dashboard

- Show daily sales, open repairs, unpaid invoices, low-stock items, and recent activity.
- Use read-only aggregate queries scoped by `shopId`.

## Later Mobile/Offline Readiness

When mobile/offline work begins later, the schema already supports:

- client-generated UUIDs
- client-generated record references
- version-based conflict detection
- `updatedAt`-based incremental sync
- soft-delete propagation
- append-only repair status and inventory movement sync

The MVP should not include sync endpoints yet, but services should be shaped so future sync ingestion can reuse the same operations.
